## 一、先看现场实测（决定哪些条目真的适合）

对 `http://192.168.1.78:8090` 实测（2026-09-22 17:20）：

| 探测项 | 实测结果 | 对结论的影响 |
|---|---|---|
| 响应头是否有 `Server`/`Via` | **无** | 8090 是 **Node 直连，前面没有反向代理** |
| `Accept-Encoding: gzip,br` 后的 `Content-Encoding` | **无** | **零压缩**：`editor.js` 等文本资源原样传输（性能审计 §1.2 现场复现） |
| `Cache-Control` / `ETag` / `Last-Modified` | **均无** | **零缓存头**（性能审计 §1.1/§1.2 现场复现） |
| `/api/sensors/values` 的 `Cache-Control` | **无** | 实时数据接口无禁缓存（API 契约审计 §2.1 现场复现） |
| 部署方式 | **Docker Compose**（容器 `pfd-editor`） | 服务器侧可承接 docker/基础设施类改动 |
| **端口 80 的 `Server` 头** | **`nginx/1.24.0 (Ubuntu)`** | 🎯 **服务器上已经装了 nginx 并已在反代后端** → 给 8090 加一个 server block 属**顺理成章的增量改动**，不需要新引入组件 |
| 端口 8090 的 `Server` 头 | **无**（Node 直连） | 8090 目前**绕过 nginx**，压缩/缓存/限流全空 |
| 安全头（nosniff/CSP/XFO） | 齐全 ✅ | 说明已部署到含安全批次的版本 |

**关键结论**：服务器**已装 nginx 1.24 且在反代后端（端口 80）**，但 **8090 绕过了它**，导致压缩/缓存/限流全空 ——
这恰好是**基础设施层**能一次解决多个条目的地方（见 §2 的 A 项），而且**不需要引入新组件**，只需给 8090 加一个 server block。

## 二、适合交给服务器侧的条目（按性价比排序）

### 🟢 A. 前置 Nginx：一次改动关掉 4 个条目（**最推荐**）

| 关联条目 | 现状 | Nginx 层怎么解 |
|---|---|---|
| 性能 §1.2 静态资源零压缩 | 文本资源 ~750KB 原样传（实测确认） | `gzip on` + `gzip_types` + `brotli`（若编译支持）→ 理论压至 ~150-180KB |
| 性能 §1.1 全量破缓存（`?v=Date.now()`） | 每请求都带时间戳，缓存完全失效 | 静态资源 `Cache-Control: public, max-age=31536000, immutable`（配合时间戳不影响正确性）+ `etag on` |
| 性能 §3.4 无并发/速率限制 | 无任何限制 | `limit_req` / `limit_conn` 限流 |
| API 契约 §2.1 实时接口不禁缓存 | 后端无 `Cache-Control`，链路任一层都可能缓存陈旧值 | 对 `/api/sensors/*` 强制 `add_header Cache-Control no-store always` |

**为什么适合服务器侧**：纯基础设施改动，**不动一行业务代码**；且审计本身就把"Nginx/CDN 接管压缩与缓存"列为可选方案（性能 §1.2 的「大厂标准」列）。
**可落地性（实测支撑）**：服务器上 **nginx 1.24.0 已在运行**（端口 80 反代后端），8090 是 Node 直连 —— 因此本项是**给现有 nginx 加一个 server block**，而非引入新组件，落地成本低、可灰度（先只对静态资源开 gzip 验证，再逐步加缓存与限流）。
**为什么推荐**：一个改动同时关掉 4 个条目，还能顺带加 TLS 与访问日志。
**风险**：低（可先只对静态资源开 gzip 验证）。**注意**：加反代后需确认 `X-Forwarded-*` 由 nginx 重写（安全审计 §4.3 已改为不信任客户端该头）。
**验收**：`curl -H 'Accept-Encoding: gzip' -D - -o /dev/null <url>` 出现 `Content-Encoding: gzip`；静态资源有 `Cache-Control`；`/api/sensors/*` 有 `no-store`。

### 🟢 B. 工程化 §3.1 · 固定镜像 digest

**现状**：`Dockerfile` 用 `FROM node:20-alpine`（可变 tag）。我在仓库侧**取不到可信 digest**（本机 Docker daemon 未运行 + registry 被网络策略拦截），**没有编造**，已在 Dockerfile 原位写明命令。
**为什么适合服务器侧**：服务器能访问 Docker Hub。
**做法**：`docker buildx imagetools inspect node:20-alpine` 取 Digest → 改 `FROM node:20-alpine@sha256:<digest>` → 重新构建。
**验收**：`docker images --digests` 显示固定 digest；`.github/dependabot.yml` 已配 docker 生态会自动提升级 PR。

### 🟢 C. 性能 §5.1 · 监控基线 / 遥测（服务器侧唯一可行）

**现状**：**零性能门禁、零 RUM、零遥测**。FPS 徽标是唯一客户端工具（本地、不留痕、不上报）。
**为什么适合服务器侧**：指标采集、日志聚合、告警都发生在服务器。
**做法（建议最小起步）**：
1. 采集：`docker compose logs` 已有**结构化 JSON**（`{"ts","level","event",...}`）→ 用轻量采集（如 `promtail`/`vector`）或定时 `docker logs --since` 落盘
2. 关键指标：`/healthz` `/readyz` 可用性（外部探活）、`/api/*` 的 502/503 计数、`proxy-timeout` 事件计数（服务端已结构化输出）
3. 告警：`event":"server-error"` / `"proxy-error"` / 健康检查连续失败 → 通知（邮件/IM webhook）
**验收**：能回答"过去 24h 服务可用率、错误率、超时次数"；健康检查失败能自动告警。

### 🟢 D. 工程化 §7.x · 日志留存与告警（部分已交接）

**现状**：容器 json-file 轮转已配（10m×3，服务器侧 Agent 已做 ✅）；**journald 主机级配置未做**（账号无免密 sudo，已如实回报）。
**适合服务器侧**：需管理员权限。
**待办**：拿到 sudo 后补 `/etc/systemd/journald.conf.d/pfd.conf`（`SystemMaxUse=500M` / `MaxRetentionSec=1month`）—— 注意容器日志走 json-file 不进 journald，**若用 docker 部署，该项可降级为可选**。

### 🟢 E. 数据一致性 §4.4 · 后端位号数据质量（需服务器/后端侧）

**现状**：实测后端目录 **274 条记录 / 273 个去重位号**，其中 **13 条位号带首尾空格**（如 `' 2#冷却水泵P0802A电流检测'`）；且演示工程引用的 5 个位号在目录中不存在（含 `供气风机` vs 后端实为 `供热气风机` 的错别字）。
**为什么适合服务器侧**：数据源在服务器侧后端，清洗必须在那里做。
**做法**：推动后端在**入库侧** trim 位号 + 加唯一约束；核对那 5 个失效位号是改名了还是从未存在。
**验收**：重新拉取目录，带空格位号数为 0；5 个失效位号确认结论（改名→前端同步 / 不存在→修正演示工程）。

### 🟡 F. 安全 · 轮换 `PFD_API_TOKEN`（我方测试引入的暴露）

**背景**：我做版本哈希比对时，把服务器 `preview.html` 的令牌注入行打印到了输出中，**该令牌已进入会话记录**（仓库无泄漏、`.env` 已忽略、令牌仅存服务器本地）。
**做法**：`openssl rand -hex 24` 重新生成 → 更新服务器 `.env` → `docker compose up -d` 重建容器。
**验收**：旧令牌访问 `/pfd-api/projects` 返回 401，新令牌 200。

### 🟡 G. 工程化 §9.3 · 灰度/蓝绿发布（可选，成本较高）

**现状**：单容器直接覆盖部署，发布即全量。
**适合服务器侧**：属部署流程。
**做法（轻量版）**：起第二端口的新容器 → 冒烟通过 → 切 nginx upstream → 保留旧容器可回滚。
**建议**：当前是内网单机部署，**收益有限，可延后**；若加上 §2A 的 nginx，届时做起来会很自然。

## 三、**不适合**交给服务器侧的条目（必须在仓库侧改）

| 维度 | 条目 | 为什么不能交出去 |
|---|---|---|
| 前端与模板层（整份清单） | 全部 | 全是 `editor.js`/`preview.html`/`templates/*` 的前端实现，服务器侧改了不生效（代码要进仓库才能部署） |
| 架构与代码质量 | §5.9 / §10.6 / §10.7 / §6.7 等 | 开发者 Agent 正在改（未提交）；且都是源码改动 |
| 性能 | §2.1 编辑器粒子仍是旧实现 | 源码改动 |
| 性能 | §3.2 代理**连接复用**（keep-alive Agent） | 属 `server.js` 代码改动，nginx 无法替代应用侧出站连接复用 |
| 性能 | §4.1 导出链路 37 个 fetch | 源码改动（服务端加 `/pfd-api/bundle` 端点也需改 `server.js`） |
| API 契约 | §1.x REST 语义、§3.x postMessage 协议、§4.x `PFDEmbed` 承诺 | 均为源码/协议定义，需在仓库侧改并随部署生效 |
| 工程化 | §1.2 覆盖率门槛、§2.5 制品归档与失败通知、§6.4 根目录文档归位 | 属 CI/仓库结构 |
| 工程化 | §10.3 / §10.5 启动脚本健壮性 | 属仓库侧脚本（`start.cmd`） |

## 四、建议的交接范围（我的推荐）

**第一批交出去（性价比最高，纯基础设施）**：
